## Goal

Full-screen 4K60 HEVC plays smoothly. The owner verdict that tripped ADR-012: software
playback is acceptable **only** for low-resolution videos. Measured on the stress clip
(4K60 HEVC, fitted to the 7680×2160 display):

| | ceiling | decode CPU | copy/frame |
|---|---|---|---|
| ship today (sw RGB32 + contiguous copy) | 72–75 fps | ~9 ms (MF threads) | 12.2 ms |
| **this plan (NVDEC + NV12 + Lock2D + in-shader YUV)** | **191–195 fps** | **~0** | 4.9 ms |

Non-goals (explicitly deferred): full zero-copy D3D11→wgpu shared-handle interop (the
measured ceiling is 3× budget without it — the endgame stays a documented escalation);
P010/10-bit HDR video output (the two-plane path leaves the door open; SDR-8-bit output
is unchanged from today); a frame-drop engine (unchanged seam).

## Decisions locked (from the spike — challenge in review if wrong)

| Question | Decision | Why (measured) |
|---|---|---|
| Which rung ships | **Rung 3 + 2 together**: MF hardware decode (D3D11 device manager + `MF_READWRITE_ENABLE_HARDWARE_TRANSFORMS`) with **NV12 output**, `IMF2DBuffer2::Lock2DSize` readback, YUV→RGB **in-shader** | 191–195 fps at 4K60 vs 72–75 today; decode CPU → ~0 |
| Not the "no-shader" hw RGB32 shortcut | rejected | weakest hw variant (115 fps at 4K, 87 on the MKV — the GPU RGB convert adds a second sync); 33 MB vs 12.4 MB/frame over the bus; and we'd still owe the NV12 path for macOS/P010 |
| Not copy-only fixes (rungs 1–2 alone) | rejected as the ship config | they raise the ceiling to only ~100 fps; the 9 ms software HEVC decode is the wall. (Rung 1's `Lock2DSize` *is* adopted — it's how the hw path reads back, and the sw path keeps its current copy untouched) |
| When hw is used | **Pixel-rate policy**: `native_w × native_h × fps ≥ 250 M px/s` → hw; below → today's software producer **byte-for-byte unchanged** | the hw readback has a ~6 ms/frame **flat sync cost** — hw is ~166–195 fps at *any* size, i.e. *slower* than software for small clips (sw: 480–1190 fps). 250 M px/s ≈ 4K30; 1080p60 (124 M) stays software |
| HDR sources (PQ/HLG transfer) | **v1 gate: hw path takes SDR transfers only**; PQ/HLG stays on the software RGB32 path, where MF's converter SDR-clamps deterministically exactly as today (`mf_video.rs` `native_color` docs) | staying YUV end-to-end means MF's video processor may pass PQ/HLG through *unconverted* in NV12 — our 8-bit shader would then mis-map brightness (the review's "no double/missed transfer application" warning, and `ColorTransform`'s 7-param TRC can't express PQ/HLG). Phase C probes what MF actually emits for an HLG clip; P010 + PQ/HLG-in-shader is the reserved follow-on that lifts the gate |
| Fallback chain | any hw failure → software producer, same session, transparently | D3D device creation (VM/no dGPU), NV12 negotiation, `IMF2DBuffer2` QI, or a first-read error each fall back; the session sees only `VideoFrame`s |
| Device lifetime | one D3D11 device + `IMFDXGIDeviceManager` **per producer run**, reused across seek `reopen_at` | seeks recreate readers constantly (spike E); recreating the *device* per seek would re-add init latency. Producer exit drops it |
| YUV→RGB correctness reference | `pb-decode/src/yuv.rs` (the fuzzed dav1d converter) is the bit-reference; the shader must match it within tolerance | one YUV truth in the codebase, already tested against real streams |

## Architecture

```
                 pixel-rate ≥ 250 M px/s AND hw setup succeeds
                                  │
        ┌─── no ─────────────────┴────────────── yes ───┐
        ▼                                               ▼
 run_video_producer (today's path,          run_video_producer_hw
 RGB32 + swizzle — UNCHANGED)               D3D11 mgr + NV12 + Lock2DSize
        │                                               │
        └────────────► VideoFrame { format, pixels, color } ◄──────────┘
                            (Rgba8)        (Nv12: Y then UV planes)
                                  │
                       VideoSession (UNCHANGED — byte budget
                       already format-agnostic via byte_len)
                                  │
                     AppCore::present_video_frame — dispatch on format
                        │                        │
                 Renderer::set_image      Renderer::set_video_nv12
                 (today's path)           two-plane ReuseSlot + WGSL convert
```

### 1. Contracts (`pb-decode`)

- **`PixelFormat::Nv12`** — new variant. `bytes_per_pixel()` is wrong for a subsampled
  format, so: add `PixelFormat::frame_bytes(w, h) -> usize` (`w·h·3/2` for NV12, the
  existing `w·h·bpp` otherwise) and migrate `VideoFrame::is_well_formed` to it. Stills
  (`DecodedImage`) never construct `Nv12`; the still-upload path gets a
  `debug_assert!`/error arm. NV12 requires even dimensions — the MF video processor
  always emits even; the producer verifies and falls back to software if not.
- **`VideoFrame.pixels` layout for `Nv12`**: tightly packed Y plane (`w·h`) followed by
  the interleaved UV plane (`w·(h/2)`) — exactly what the spike's `copy_nv12_2d` packs.
- **`VideoColorInfo`** gains the shader's YUV parameters:
  `yuv_matrix: YuvMatrix { Bt601, Bt709, Bt2020 }` + the existing `full_range` flag
  becomes load-bearing (today it is recorded but unused — RGB32 frames were already
  converted by MF). Mapping: `MF_MT_YUV_MATRIX` / `MF_MT_VIDEO_NOMINAL_RANGE` read from
  the **negotiated output type**; when absent, the standard heuristic (≥720p → BT.709,
  else BT.601; BT.2020 when the primaries say so). `transform` keeps carrying
  primaries + transfer exactly as today — the shader chain is
  `range-expand → yuv_matrix → (existing) transform → scene-linear`.
  **Single-application contract (rev2):** for `Rgba8` frames the producer (MF) has
  applied matrix+range and `yuv_matrix` is inert; for `Nv12` frames *nobody* upstream
  has — the consumer applies matrix+range **exactly once**. This is stated in the
  field docs and enforced by the color-parity test (Testing 4): the same source frame
  through both paths must match, which fails on any double or missed application.
- **`VideoProducerEvent::Opened`** gains `frame_bytes: u64` — the session's credit-size
  correction currently hardcodes `w·h·4` (`video_session.rs` drain), which would
  overestimate NV12 by 2.67× and under-parallelize the pipeline (the exact bug the
  2/3×-speed fix addressed, in the other direction).

### 2. Renderer (`pb-render`)

- **Trait**: one new method with a **default implementation**:
  `fn set_video_nv12(&mut self, y: &[u8], uv: &[u8], w, h, yuv: YuvParams, color: ColorTransform)`
  whose default converts on CPU via the `yuv.rs` reference and calls `set_image`. This
  keeps every other `Renderer` impl working, gives tests a WARP-free correctness path,
  and is the A/B lever (`PB_VIDEO_CPU_CONVERT=1` forces it in the shipping renderer).
- **`WgpuRenderer` override** — the real path:
  - `ReuseSlot` grows an optional UV plane: Y as `R8Unorm` (`w×h`), UV as `Rg8Unorm`
    (`w/2 × h/2`). Same reuse discipline as phase 3: same-geometry frames upload in
    place; a geometry/format change rebuilds the slot + bind group.
  - A second scene bind-group layout (`y_tex + uv_tex + sampler + uniform`) and scene
    pipeline. The WGSL fragment: sample Y and UV (bilinear on both — chroma siting
    left/center differences are below visual threshold at fit scale, documented),
    range-expand (limited: `(Y−16/255)·255/219`, chroma `−128/255·255/224`), apply the
    3×3 matrix picked by a uniform index, then fall into the **same** color-transform
    → scene-linear code the RGB path uses (factor the existing WGSL color functions
    into a shared module string; two entry points, zero duplicated math).
  - The YUV params ride the existing per-slot uniform buffer (it is `COPY_DST`;
    extend the struct — matrix index + range flag pack into one vec4 spare).
  - Upload: two `copy_buffer_to_texture` from the existing `StagingUpload` ring
    (256-byte row alignment handled the same way the RGBA path does). **The
    never-wait property is preserved** (rev2): the two-plane upload uses the same
    bounded mapped-buffer pool discipline — it must never block on GPU completion
    on the event-loop thread; `present_path_churn` extends to assert it.
- **Not** a change to the tone-map/present pass — NV12 lands in the same fp16 scRGB
  intermediate after conversion; SDR/HDR output paths are untouched.

### 3. Windows producer (`pb-decode/src/mf_video_producer.rs` + a new `mf_hw.rs`)

- `mf_hw::dxgi_manager()` — promote the spike's helper: D3D11 hardware device
  (`D3D11_CREATE_DEVICE_VIDEO_SUPPORT`, multithread-protected) wrapped in
  `MFCreateDXGIDeviceManager` + `ResetDevice`. Any error → `None` → software.
- Producer entry decides once per session:
  `hw = policy(native_w, native_h, fps) && dxgi_manager available && NV12 negotiates`.
  The policy function is pure + unit-tested; `PB_VIDEO_FORCE_HW=0|1` overrides for
  A/B and tests (absent fps metadata → assume 30).
- Reader creation (initial + every seek `reopen_at`): the same attributes as today
  **plus** `MF_SOURCE_READER_D3D_MANAGER` + `MF_READWRITE_ENABLE_HARDWARE_TRANSFORMS`,
  reusing the one manager. Advanced video processing stays on (rotation + fitted
  scaling now run on the GPU video processor).
- `read_one` (hw variant): `GetBufferByIndex(0)` → QI `IMF2DBuffer2` →
  `Lock2DSize(Read)` → pack Y+UV (the spike's `copy_nv12_2d`). QI failure → fall back
  to `ConvertToContiguousBuffer` with NV12 stride math (still correct, slower); a
  ReadSample error fails the session exactly as today.
- Note (from MF semantics, verify in phase C): `MF_READWRITE_ENABLE_HARDWARE_TRANSFORMS`
  *enables* hw MFTs — a codec with no NVDEC support (e.g. old VC-1) silently uses the
  software MFT with the D3D manager attached. That combination still works; the policy
  threshold means we only ever pay it for genuinely heavy clips.
- Poster/probe (`mf_poster.rs`) stays software RGB32 — one frame, latency-bound, and it
  keeps the no-GPU-dependency property. **Color parity poster↔playback becomes a
  tested property instead of by-construction** (see Testing 4) since playback now does
  its own YUV→RGB.
- **Lifetime ordering (rev2):** retiring readers (`retire_reader`, off-thread) hold COM
  references into the DXGI manager's device; the producer keeps the manager alive until
  its thread exits, and COM refcounting covers the overlap — documented so a future
  "drop the manager early" cleanup doesn't reintroduce a use-after-release.

### 4. AppCore glue (`pb-app-core`)

- `poll_video`'s present arm and `video_frame_step`'s `Present` arm share a new
  `present_video_frame(&VideoFrame)` helper that dispatches on `frame.format`:
  `Rgba8` → `set_image` (unchanged), `Nv12` → `set_video_nv12`.
- Nothing else: session, budgets, seeking, audio, the playback bar — all
  format-agnostic already.

## Phases (each lands with gates green; owner smoke closes C)

**A. Contracts + CPU-convert spine.** `PixelFormat::Nv12` + `frame_bytes`,
`VideoColorInfo.yuv_matrix`, `Opened.frame_bytes`, session credit fix + test,
`Renderer::set_video_nv12` default impl (via `yuv.rs`), `present_video_frame` dispatch.
A hand-built NV12 `VideoFrame` plays correctly through the CPU fallback (unit +
session-level test). No producer changes yet — pure plumbing, all platforms.

**B. GPU convert.** Two-plane `ReuseSlot`, the NV12 scene pipeline + shared WGSL color
functions, `StagingUpload` two-plane upload, `WgpuRenderer::set_video_nv12` override.
Golden test on WARP: synthetic NV12 gradient rendered offscreen vs the `yuv.rs` CPU
reference (per-channel tolerance ±2/255, all three matrices × both ranges).
`present_path_churn` extended to the NV12 slot (no per-frame allocation).

**C. The hardware producer.** `mf_hw.rs`, policy + env override (incl. the SDR
transfer gate), hw `read_one`, seek-path manager reuse, fallback chain,
`Opened.frame_bytes` wiring. Integration tests on the committed fixture with
`PB_VIDEO_FORCE_HW=1` (tolerate graceful fallback on GPU-less CI — assert *a* path
produces well-formed monotonic frames, log which). Probes on real clips (rev2):
a **portrait/rotated** clip (the GPU video processor must apply rotation identically
to the poster path) and an **HLG/PQ** clip (what does MF emit in NV12 — passthrough
or SDR-converted? decides whether the transfer gate can ever be lifted pre-P010).
Measurements: copybench re-run recorded in the spike doc; `PB_VIDEO_PERF_CLIP`
P→first-frame (budget: ≤ today + 30 ms for device creation — if worse, move device
creation off the open critical path); owner full-screen 4K60 smoke = the acceptance.
Docs: CLAUDE.md video section, CHANGELOG (`Changed`), status doc.

## Testing summary

1. **Unit:** policy function (rates around the threshold, fps-absent default,
   overrides); MF attr → `YuvMatrix`/range mapping; NV12 `frame_bytes`/well-formedness
   (odd-dimension rejection).
2. **Golden (WARP CI):** shader convert vs `yuv.rs` reference — gradient covering full
   Y/U/V range, {601, 709, 2020} × {limited, full}.
3. **Session-level:** NV12 frames through preroll/present/seek on fake producers
   (frames are just bytes to the session — one test proves the budget math).
4. **Color parity:** same real frame via software-RGB32 path and hw-NV12 path (or CPU
   reference when no GPU), compared within a perceptual tolerance — the guard that the
   in-shader matrix/range matches what MF's converter did for the poster.
5. **Perf (opt-in, release):** copybench; P→first-frame p50/p95; steady-state
   full-screen owner smoke on the two stress clips + the H.264 VFR clip + an MKV.
6. **No-trace:** unchanged (`viewing_*_writes_nothing_to_disk` still passes — the hw
   path touches GPU memory, never disk).

## Risks / open questions for review

1. **Threshold value (250 M px/s).** Data says 4K30+ needs hw and 1080p60 doesn't.
   But an 8K clip: hw NV12 readback scales to ~20 ms/frame (~50 fps) — 8K60 would need
   the zero-copy endgame; 8K30 fits. Accept as documented limitation?
2. **Chroma siting + bilinear UV** — half-texel chroma offset is ignored (fit-scale
   display; invisible in practice). Flag if you want exact cositing math in the shader.
3. **Battery/thermals on laptops:** hw decode is *better* there; the flat readback cost
   is a desktop-GPU number. Policy is resolution-based, not platform-based — fine?
4. **Device-lost mid-stream** (driver reset): surfaces as a read error → session
   `Failed` → toast; `P` restarts (fresh device). Acceptable v1 recovery?
5. **10-bit HEVC (Main10):** MF converts P010→NV12 (8-bit) — same depth as today's
   RGB32 output, no regression; P010/HDR is the reserved follow-on. Confirm punt.
6. **A/B levers:** `PB_VIDEO_FORCE_HW` + `PB_VIDEO_CPU_CONVERT` env vars (dev-only,
   undocumented) — enough, or do you want a Settings toggle for hw decode?
7. **The ~6 ms readback sync** is driver behavior we exploit but don't control; if a
   future driver regresses it, the zero-copy rung is the escape hatch. The seam
   (producer swap) is already shaped for it.
8. **The HDR gate's cost (rev2):** modern iPhones record HDR (HLG/Dolby Vision) by
   default, so their 4K60 clips stay on the software path — i.e. still not smooth —
   until either the phase-C probe shows MF SDR-converts within NV12, or the P010
   follow-on lands. Flagging explicitly: if smooth HDR 4K60 is required for ship,
   P010 moves from "reserved follow-on" into this task's scope.
