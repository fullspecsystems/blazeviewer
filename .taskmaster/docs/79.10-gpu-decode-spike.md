# Task 79.10 — GPU decode spike: the copy/decode ladder, measured

_2026-07-11, RTX 5090 / 7680×2160 box. Harness:
`cargo run --release -p pb-decode --example video_probe -- copybench <file> --fit 7680 2160 --frames 240`.
One warmup frame excluded; read = `ReadSample` (MF pipelines decode on its own
threads, so read-vs-copy split is indicative, ceiling is the truth)._

## Results (steady-state ceiling, fps)

| mode | 4K60 HEVC (IMG_0060.MOV) | 1920×1440 H.264 VFR | 1102×720 HEVC MKV |
|---|---|---|---|
| rgb32/contig — **ship today** | **72–75** | 264 | 480 |
| rgb32/lock2d — rung 1 | 87–99 | 564 | 499 |
| nv12/lock2d — rung 2 CPU side | 96–107 | 1190 | 1173 |
| **hw nv12/lock2d — rung 3 CPU side** | **191–195** | 175 | 166 |
| hw rgb32/lock2d — "no-shader" option | 115 | 157 | 87 |

Per-frame details on the 4K60 stress clip:
- ship today: copy p50 **12.2 ms** (`ConvertToContiguousBuffer`'s internal 33 MB copy + swizzle)
- rung 1 (`Lock2DSize`): copy p50 **3.3–3.8 ms** — MF's internal copy is ~70 % of the copy cost
- rung 2 (NV12, 12 bpp): copy p50 **0.86 ms**; software HEVC decode (~8–10 ms) becomes the wall
- rung 3 (NVDEC): read p50 **0.08 ms** (decode CPU ≈ 0), copy p50 **4.9 ms** (GPU→CPU staging readback of 12.4 MB)

## The two structural findings

1. **Software 4K60 HEVC cannot be fixed by copy optimizations alone.** Rungs 1–2
   raise the ceiling to ~100 fps but the decode itself (~9 ms/frame) leaves no
   headroom at 60 fps with the app's upload/present on top. Hardware decode is
   the answer for heavy clips, confirming the ADR-012 escalation.
2. **The hardware path has a ~6 ms/frame flat cost** (the `Lock2D` readback
   synchronizes with the GPU pipeline — it is NOT bandwidth: 1.2 MB reads back no
   faster than 12.4 MB). So hw is a ~166–195 fps ceiling at *any* resolution:
   3× budget at 4K60, but *slower than software* for small/easy clips
   (software does 480–1190 fps there).

## Ship decision

**Hardware decode + NV12 output + `Lock2DSize` readback + YUV→RGB in-shader**,
picked by a **pixel-rate policy**, software RGB32 path unchanged as the fallback:

- `native_w × native_h × fps ≥ ~250 M px/s` (≈ 4K30 and up) → hw producer
  (D3D11 device manager + `MF_READWRITE_ENABLE_HARDWARE_TRANSFORMS`, NV12).
- below that, or if device/manager creation or hw negotiation fails (VM, exotic
  codec, no dGPU) → today's software RGB32 producer, byte-for-byte unchanged.

Why NV12 + shader and not the tempting "no-shader" hw RGB32 (zero renderer
work): it's the weakest hw variant (115 fps at 4K, 87 on the MKV — two GPU
syncs), it doubles bus traffic (33 MB vs 12.4 MB/frame at 4K), and the NV12
shader path is exactly what macOS parity (VideoToolbox → NV12) and 10-bit HDR
video (P010) will reuse.

## Implementation results (2026-07-11, phases A–C landed)

- P→first-frame on the 4K60 HEVC stress clip through the real hw producer +
  session: **p50 127 ms / p95 224 ms** — vs the software baseline p50 183 / p95
  320. The hw path is *faster* to first frame despite D3D device creation.
- GPU shader convert golden-matches the CPU reference within quantization for
  {601, 709, 2020} × {limited, full} on the real adapter.
- Remaining before sign-off: owner full-screen 4K60 smoke; portrait-clip
  rotation probe; HLG probe (needs a corpus clip — none on disk yet).

## Build list (the implementation phase)

1. `VideoFrame`: an NV12 pixel-format variant (packed Y + interleaved UV,
   `byte_len` = w·h·3/2) + the YUV matrix/range riding `VideoColorInfo`.
2. `pb-render`: two-plane texture in the `ReuseSlot` (R8 Y + Rg8 UV), scene-pass
   WGSL branch — range expansion + YUV matrix → existing primaries/transfer
   transform → tone map. Golden test vs the CPU converter (`yuv.rs`).
3. `mf_video_producer`: the hw reader variant (manager + NV12 + `Lock2DSize`),
   the pixel-rate pick, fallback to the software path on any failure.
4. Budget math already generalizes (`byte_len`); session untouched.
5. Measure: P→first-frame regression check (hw reader creation adds D3D device
   setup), the opt-in perf tests, and the owner's full-screen smoke.
